Lesson 3 — Mastering /opsx:explore

How to probe codebases, unearth hidden architectural invariants, and evaluate trade-offs before writing a single line of spec or code

1. Why the Explore Phase Exists

In traditional development and naive AI prompting, developers commit the Premature Solutioning Anti-Pattern:

  [ The Premature Solutioning Trap ]
  Idea ───► Immediately write code / draft spec ───► Hit hidden DB constraint in step 4
                                                ───► Rewrite half the implementation

When you jump straight into /opsx:propose with a fuzzy idea, the AI generates proposals based on superficial assumptions. In a rich codebase like Personal-Library, it might miss that:

  • Books have a 2-tier scoping model: Global Catalog vs. User Library Book.
  • Collections have a hard limit of 4 hierarchy levels.
  • All endpoints under /api/v1/users/me/** must extract userId from UserPrincipal, never from URL query parameters.
💡 The Principle of /opsx:explore /opsx:explore is your Thinking Partner. It operates under a strict contract: investigate, challenge, uncover risks, and compare trade-offs without writing a single file to disk or modifying state.

2. The Anatomy of an Effective Explore Session

An exploratory query is not just a casual chat. A high-leverage /opsx:explore prompt follows a 4-part structure:

/opsx:explore

I want to add User-Defined Book Tags to our personal library.

1. Context Investigation: Examine how LibraryBook, Note, and Category are structured in org.example.library.*.
2. Invariant Discovery: What existing security, multi-tenancy, and database patterns must tags adhere to?
3. Architectural Trade-offs: Compare: (A) A dedicated Tag entity with a join table vs. (B) a PostgreSQL array/JSONB column vs. (C) reusing the Category entity.
4. Edge Cases: What happens on duplicate tag creation, tag deletion with associated books, or cascading user deletions?

3. What the AI's Exploration Report Looks Like

When given that structured query against Personal-Library, the AI produces a structured breakdown:

Section 1: Codebase Findings

  • Category is global/admin-managed (defined in category/domain/Category.java), whereas tags must be strictly user-owned.
  • LibraryBook already has ownership bound to user_id. Tags must link to LibraryBook, not the global Book catalog entity.
  • Existing migrations use Liquibase (located at library-app/src/main/resources/db/changelog/). Any new table requires an XML changelog entry.

Section 2: Trade-Off Matrix

Option Pros Cons Verdict
Option A: Dedicated Tag Entity + Join Table Relational integrity, easy indexing, user-scoped uniqueness, standard JPA query support via Specifications. Requires new entity, repository, and join table migration. Recommended — Matches project architecture.
Option B: PostgreSQL Array / JSONB No join table needed. Breaks H2 slice testing compatibility; harder to enforce case-insensitive uniqueness per user across all books. Rejected.
Option C: Reusing Category Zero new tables. Pollutes global admin taxonomy with private user tags; violates domain boundary. Rejected.

Section 3: Invariants & Non-Goals Discovered

  • Invariant: Tag names must be normalized (trimmed, case-insensitive uniqueness per user).
  • Invariant: Maximum 50 tags per user to prevent unbounded joins and memory DOS.
  • Non-Goal: Hierarchical tags (e.g. tech/java/spring) are out of scope for v1. Tags are flat strings.
  • Non-Goal: Public tag sharing between users is out of scope.

4. The Transition: From Explore to Propose

Once you are satisfied with the exploratory findings, you synthesize them directly into the proposal command:

/opsx:propose book-tags --option=A --max-tags=50 --scope=user-flat

Notice the massive difference between this and naive prompting: because you explored first, the resulting proposal is already aligned with your architecture, security rules, and database conventions. Zero guesswork.

5. When to Use /opsx:explore vs. Going Straight to Propose

Scenario Recommended Action Rationale
Adding a brand new feature or domain concept /opsx:explore first Uncovers architectural seams, security patterns, and DB trade-offs before committing.
Refactoring an existing cross-cutting service /opsx:explore first Discovers all callers and hidden dependencies across package seams.
Adding a standard CRUD field to an existing DTO/entity Go straight to /opsx:propose Low architectural ambiguity; trade-offs are already known.
Fixing a localized bug with a known stack trace Go straight to /opsx:propose (or direct fix) Exploration overhead not required for deterministic single-line fixes.

7. Knowledge Check

1. What is the primary output of an /opsx:explore command?

  • A committed Git branch with test cases
  • A set of markdown files in openspec/changes/
  • An interactive chat analysis with trade-offs and zero disk changes
  • A compiled JAR file with updated dependencies
✅ Correct! /opsx:explore is strictly an in-memory thinking-partner session. It outputs analysis in chat and writes zero files to disk.
❌ /opsx:explore creates no files on disk. Its output is an analytical report in chat designed to clarify requirements before creating artifacts.

2. Why should "Non-Goals" be identified during the explore phase?

  • To explicitly bound the scope and prevent AI agent scope creep
  • To reduce the number of Git branches created
  • To automatically delete obsolete classes from the project
  • To disable Java compiler warnings during builds
✅ Correct! Declaring Non-Goals prevents the AI from generating unwanted abstractions (like hierarchical tagging when you only asked for flat tags).
❌ Non-Goals explicitly define what is *out of scope*, preventing the AI from adding speculative complexity and unneeded abstractions.
