Lesson 2 — Your First Spec with OpenSpec

Hands-on: install OpenSpec, initialize it on Personal-Library, and write a real delta spec for a Book Tags feature

What You'll Do (Not Just Read)

By the end of this lesson you will have:

  1. Installed the OpenSpec CLI on your machine
  2. Initialized OpenSpec inside D:\Personal-Library
  3. Written a real proposal for adding user-defined book tags
  4. Generated a delta spec describing the exact changes
  5. Used the spec to guide an AI agent toward implementation
📚 Why "Book Tags"? Your Personal-Library already has categories (admin-managed, global), but no user-defined tags — lightweight, personal labels like "vacation reads", "gift ideas", or "re-read". It's a small, self-contained feature that touches existing entities (LibraryBook), needs a new package (tag), and has clear domain rules. Perfect for a first spec.

Step 1 — Install OpenSpec CLI

OpenSpec requires Node.js v20.19+. Open a terminal and run:

npm install -g @fission-ai/openspec@latest

Verify installation:

openspec --version
💡 Don't have Node.js? Download it from nodejs.org. The LTS version (v22+) works fine.

Step 2 — Initialize OpenSpec on Personal-Library

Navigate to your project and run:

cd D:\Personal-Library
openspec init

The CLI will ask you to select your AI coding tool (Cursor, Claude Code, Copilot, etc.). Pick whichever you use — the spec files are the same regardless.

After initialization, you'll see a new directory structure:

Personal-Library/
└── openspec/
    ├── specs/          ← Living specs (system state documentation)
    └── changes/        ← Scoped directories for each new feature/change
⚠ Checkpoint — stop and verify Before continuing, confirm that the openspec/ directory was created in your project root. If it wasn't, check that Node.js is v20.19+ and retry.

Step 3 — Create a Change Proposal

Now you'll propose a new feature. In your AI assistant's chat window (not the terminal), type:

/opsx:propose book-tags

This creates a scoped directory under openspec/changes/book-tags/ containing:

FilePurposeWho writes it
proposal.md Business intent — what and why AI drafts, you review
design.md Technical architecture — how AI drafts, you review
tasks.md Ordered implementation checklist AI generates from design
specs/<capability>/spec.md Delta spec — exact ADDED/MODIFIED/REMOVED requirements AI generates, you approve
🔑 This is the SDD moment In vibe coding, you'd just say "add tags to books" and let the AI go. Here, the AI produces reviewable artifacts first. You approve the spec before any code is written. That's the fundamental shift.

Step 4 — Review and Refine the Proposal

Open openspec/changes/book-tags/proposal.md. The AI will have drafted something. Your job is to challenge it against these domain rules specific to your project:

Domain Rules You Should Enforce in the Spec

  1. Tags are user-scoped — each user has their own tags; no global tag catalog
  2. Tags apply to LibraryBooks — not to global Books (consistent with how ratings, notes, and collections work in your app)
  3. Many-to-many — a LibraryBook can have multiple tags; a tag can be on multiple LibraryBooks
  4. Tag name constraints — max 30 characters, case-insensitive uniqueness per user, trimmed whitespace
  5. Soft limit — a user can have at most 50 tags (prevents abuse)
  6. Package-by-feature — new tag package following the same structure as note, quote, etc.

If the AI's proposal doesn't match these rules, tell it to revise. This is the human-in-the-loop review that makes SDD valuable.

💡 How to give feedback Don't just say "looks good." Be specific: "The proposal should clarify that tags are user-scoped, not global. Also, add a 50-tag limit per user." The more precise your feedback, the better the spec.

Step 5 — Examine the Delta Spec

After the proposal and design are approved, look at the delta spec. It should contain sections like:

## ADDED Requirements

### Tag Entity
- Tag entity with fields: id (Integer), name (String, max 30 chars), user (User)
- Unique constraint on (name, user_id) with case-insensitive comparison
- Liquibase migration: create `tags` table, `library_book_tags` join table

### Tag REST API
- POST   /api/v1/users/me/tags          — create a tag
- GET    /api/v1/users/me/tags          — list user's tags
- PUT    /api/v1/users/me/tags/{id}     — rename a tag
- DELETE /api/v1/users/me/tags/{id}     — delete tag (removes from all books)

### LibraryBook-Tag Association
- PUT    /api/v1/users/me/library-books/{id}/tags  — set tags on a book
- GET filter: LibraryBookSearchCriteria gains `tagIds` field

## MODIFIED Requirements

### LibraryBookDto
- Add `tags` field (List<TagDto>) to LibraryBookDto response

### LibraryBookSearchCriteria
- Add `tagIds` filter to existing search criteria

## REMOVED Requirements

(none)

Compare this against the domain rules from Step 4. Does it match? Is anything missing? Is anything contradicting your project's conventions?

Step 6 — Apply the Spec

Once you've approved the delta spec, tell the AI to implement it:

/opsx:apply book-tags

The AI will now implement the tasks.md checklist, strictly following the spec. Watch what happens differently compared to vibe coding:

Vibe CodingOpenSpec SDD
AI invents the API shape on the fly API shape was decided in the spec and approved by you
AI might forget your package-by-feature convention Spec explicitly says "new tag package"
AI might put tags on global Books Spec says "tags apply to LibraryBooks only"
No record of why decisions were made Proposal + design + delta spec = full audit trail

Step 7 — Archive

After verifying the implementation works:

/opsx:archive book-tags

This merges the delta spec into your living openspec/specs/ documentation and files the change directory away. Your project's specs now reflect the new reality — tags exist.

Reflection — What You Just Did

You completed one full cycle of the SDD loop on a real project:

  PROPOSE → REVIEW → APPLY → ARCHIVE
     ↑                           |
     └───── next change ─────────┘

The key insight: the spec was the bottleneck, not the code. You spent most of your time reviewing and refining the proposal. The implementation was fast because the AI had a clear, bounded contract to work against.

🎯 Compare this to your vibe coding experience

Think about the last time you asked an AI to add a feature to one of your projects. How many times did it go off-track? How many times did you have to course-correct mid-implementation? The spec front-loads that alignment.

Knowledge Check

1. What does the /opsx:propose command produce?

  • Immediately generates source code
  • A proposal, design, tasks, and delta spec for review
  • A Liquibase migration script
  • An OpenAPI YAML specification
✅ Correct! /opsx:propose creates reviewable artifacts — no code is generated until you approve and run /opsx:apply.
❌ Not quite. /opsx:propose generates spec artifacts (proposal, design, tasks, delta spec) — not code. Code comes later with /opsx:apply.

2. A delta spec for adding Book Tags would primarily contain which section?

  • REMOVED Requirements only
  • MODIFIED Requirements only
  • ADDED Requirements with some MODIFIED
  • A full system specification
✅ Correct! A new feature is mostly ADDED requirements, with some MODIFIED (e.g., adding a tags field to LibraryBookDto).
❌ Since Book Tags is a new feature, the delta spec is mainly ADDED requirements (new entity, new endpoints) with small MODIFIED sections (adding tags to existing DTOs). It's never a full system spec — that's the whole point of deltas.

3. What happens when you run /opsx:archive?

  • It deletes all OpenSpec files from the project
  • It reverts the code changes to pre-spec state
  • It runs the test suite and reports coverage
  • It merges the delta spec into living docs and files the change
✅ Correct! Archive merges your delta changes into the global openspec/specs/ living documentation, keeping your project specs in sync with reality.
❌ /opsx:archive merges the delta spec into the living documentation (openspec/specs/) and files the completed change. It's the "sync" step that keeps your specs up to date.
