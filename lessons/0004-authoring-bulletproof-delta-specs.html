Lesson 4 — Authoring Bulletproof Delta Specs & Artifacts

Mastering the four core OpenSpec artifacts: proposal.md, design.md, tasks.md, and formal Delta Spec grammar with BDD scenarios

1. The Four Artifacts of a Change Workspace

When you run /opsx:propose <id>, OpenSpec initializes four distinct files inside openspec/changes/<id>/. Each file answers one fundamental engineering question:

File Question Answered Primary Audience Key Focus
proposal.md Why & What? Product / Team / Reviewers User value, problem statement, strict scope boundaries, non-goals.
design.md How? Architect / Senior Dev / Agent JPA entity diagrams, API contracts, Liquibase migration strategy, error codes.
tasks.md In What Order? AI Implementation Agent Dependency-ordered, checkable task list with automated test verification steps.
specs/<cap>/spec.md What Exactly Changes? Living Spec Engine / Agent Granular requirement deltas with BDD GIVEN / WHEN / THEN acceptance criteria.

2. Deep-Dive: The Delta Spec Grammar

The delta specification (under specs/<capability>/spec.md) is the mathematical heart of OpenSpec. It must adhere to a strict 3-section grammar:

Section A: ## ADDED Requirements

Describes completely new capabilities. Each requirement must have a unique identifier (e.g. REQ-TAG-001) and formal BDD scenarios:

## ADDED Requirements

### REQ-TAG-001: User Tag Creation
An authenticated user MUST be able to create a custom tag scoped uniquely to their account.

- **GIVEN** an authenticated user with ID 42
- **WHEN** a POST request is sent to `/api/v1/users/me/tags` with payload `{"name": "science-fiction"}`
- **THEN** a new Tag entity is persisted with `user_id = 42` and `name = "science-fiction"`
- **AND** a `201 Created` status is returned with body `TagDto(id=1, name="science-fiction")`

### REQ-TAG-002: Tag Name Normalization and Duplicate Prevention
Tag names MUST be stored in trimmed lowercase, and duplicates for the same user MUST be rejected.

- **GIVEN** user 42 already has a tag named `"history"`
- **WHEN** user 42 posts a new tag with payload `{"name": "  HISTORY  "}`
- **THEN** no database record is created
- **AND** a `400 Bad Request` status is returned with code `"error.tag.already_exists"`

Section B: ## MODIFIED Requirements

Describes changes to existing capabilities. It must specify the previous contract (WAS) and the updated contract (NOW):

## MODIFIED Requirements

### REQ-LIBBOOK-003: LibraryBook Retrieval Response
- **WAS**: `GET /api/v1/users/me/library-books/{id}` returned `LibraryBookDto` containing ID, status, rating, notes count, and location.
- **NOW**: MUST include an additional field `tags: List<TagDto>` containing all active tags attached to this library book.

Section C: ## REMOVED Requirements

Documents capabilities or fields being deprecated or deleted, accompanied by explicit architectural rationale:

## REMOVED Requirements

### REQ-LEGACY-004: Ad-hoc Freeform Category Text Field
- **REASON**: Superseded by structured User Tags and global Admin Categories.
- **ACTION**: Drop `custom_category` column from `library_books` table via Liquibase migration.

3. Structuring design.md for Spring Boot Monoliths

For a Spring Boot application like Personal-Library, a production-grade design.md should include five mandatory technical sections:

  1. Package Seam: Define the package path (e.g. org.example.library.tag.*) containing controller, service, repository, domain, dto, and mapper.
  2. Database & Liquibase Changeset: 
    <!-- db/changelog/changes/042-create-tags-table.xml -->
<createTable tableName="tags">
    <column name="id" type="BIGSERIAL" autoIncrement="true">
        <constraints primaryKey="true" nullable="false"/>
    </column>
    <column name="name" type="VARCHAR(30)">
        <constraints nullable="false"/>
    </column>
    <column name="user_id" type="BIGINT">
        <constraints nullable="false" foreignKeyName="fk_tag_user" references="users(id)"/>
    </column>
</createTable>
<addUniqueConstraint tableName="tags" columnNames="user_id, name" constraintName="uk_tag_user_name"/>
  3. Entity Relationships: @ManyToMany join table library_book_tags between LibraryBook and Tag.
  4. Error Catalog: Define exact error codes handled by RestControllerExceptionHandler (e.g., error.tag.not_found, error.tag.limit_exceeded).
  5. Performance & Indexing: Composite index on tags(user_id, name) and index on library_book_tags(library_book_id).

4. Structuring tasks.md: The Phased Execution Contract

Tasks must be broken into sequenced phases with explicit test-first checkpoints. This prevents the AI from attempting to write controllers before repositories exist:

# Tasks: User Book Tags

## Phase 1: Database & Persistence
- [ ] 1.1 Create Liquibase migration `042-create-tags-table.xml` and include in `db.changelog-master.xml`
- [ ] 1.2 Implement `Tag` entity in `org.example.library.tag.domain.Tag`
- [ ] 1.3 Implement `TagRepository` with `findByUserIdAndNameIgnoreCase` and `findAllByUserId`
- [ ] 1.4 Add `TagRepositoryIT` integration test using Testcontainers PostgreSQL

## Phase 2: DTOs, Mappers & Service Layer
- [ ] 2.1 Create `TagDto`, `CreateTagRequest`, and `UpdateTagRequest`
- [ ] 2.2 Create `TagMapper` with MapStruct
- [ ] 2.3 Implement `TagService` interface and `TagServiceImpl` with 50-tag limit enforcement
- [ ] 2.4 Write unit tests in `TagServiceTest` covering business rules and duplicate detection

## Phase 3: Web Controller & API Integration
- [ ] 3.1 Implement `TagController` under `@RequestMapping("/api/v1/users/me/tags")`
- [ ] 3.2 Add tag association endpoints in `LibraryBookController`
- [ ] 3.3 Write MockMvc tests in `TagControllerTest` verifying security and HTTP status codes

## Phase 4: Verification & Sync
- [ ] 4.1 Run full Maven build: `./mvnw clean verify`
- [ ] 4.2 Validate spec compliance with `openspec validate 20260830-book-tags`

6. Knowledge Check

1. In an OpenSpec delta spec, what does the ## MODIFIED Requirements section document?

  • Database passwords that need to be changed in production
  • Classes that were deleted during a Git merge conflict
  • Existing capabilities that are changing, with "WAS" and "NOW" descriptions
  • Comments left by team members during a PR code review
✅ Correct! ## MODIFIED Requirements explicitly documents behavioral changes to existing capabilities using WAS / NOW clauses.
❌ ## MODIFIED Requirements captures modifications to existing behavior, explicitly comparing what was before (WAS) with what is expected now (NOW).

2. Why should tasks.md be organized into phased, sequential milestones?

  • To allow the AI to guess random files to edit simultaneously
  • To enforce logical dependency order (DB → Domain → Service → Controller → Tests)
  • To bypass automated integration tests during compilation
  • To automatically format HTML documents in the browser
✅ Correct! Phasing prevents the AI from generating controllers or DTOs before the underlying domain entities and repositories are in place.
❌ Phasing ensures tasks are executed in strict dependency order (persistence first, then service, then controller and tests).
