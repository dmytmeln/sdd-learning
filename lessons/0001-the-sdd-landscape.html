Lesson 1 — The SDD Landscape

Why spec-driven development emerged, and the three methodologies you'll learn

The Problem: Vibe Coding Doesn't Scale

You open a chat window, type "build me a REST API for user management", and the AI spits out code. It works — for the first 30 minutes. Then you ask for auth, and it rewrites half the controller. You ask for pagination, and it forgets the auth. By hour two, you're debugging AI-generated spaghetti you didn't write and don't fully understand.

This is vibe coding — unstructured, conversational prompting. It's the default mode for most developers using AI assistants today. It works fine for throwaway scripts and small experiments. It falls apart for anything you intend to maintain.

⚠ The three failure modes of vibe coding
  1. Context drift — the AI forgets earlier decisions and contradicts itself
  2. Hallucination under ambiguity — without a spec, the AI invents requirements
  3. Invisible architecture debt — no record of why decisions were made

Spec-driven development is the emerging antidote. Instead of chatting your way to code, you write a specification first, then hand it to the AI as a contract. The spec becomes the source of truth — not the chat history.

What Is Spec-Driven Development?

At its core, SDD follows a simple loop:

  ┌───────────────┐
  │  1. SPECIFY   │  ← Human writes/reviews a structured spec
  └──────┬────────┘
         ▼
  ┌───────────────┐
  │  2. PLAN      │  ← AI (or human) breaks spec into tasks
  └──────┬────────┘
         ▼
  ┌───────────────┐
  │  3. IMPLEMENT │  ← AI executes tasks against the spec
  └──────┬────────┘
         ▼
  ┌───────────────┐
  │  4. VERIFY    │  ← Check code against spec; update living docs
  └──────┘────────┘
         │
         └──→ Loop back to step 1 for next change

Every SDD methodology implements this loop differently. The differences lie in how much ceremony, who does what, and how specs evolve.

The Spectrum: Three Levels of Rigor

Industry thinkers like Martin Fowler classify SDD approaches on a spectrum (martinfowler.com):

Level What Happens to the Spec Examples
Spec-First Written upfront, may be discarded after implementation Claude plan mode, Cursor Composer
Spec-Anchored Living docs — spec stays in sync with code over time OpenSpec, Spec Kit, AWS Kiro
Spec-as-Source Spec is the source code; actual code is generated & disposable Tessl

The three methodologies you asked about — OpenSpec, Spec Kit, and BMAD — all sit in the Spec-Anchored tier. They keep specifications alive as the project evolves.

Meet the Three Methodologies

🔹 OpenSpec (by Fission AI)

Philosophy: Lightweight, change-centric. Designed especially for brownfield projects — existing codebases where writing full specs from scratch would be impractical.

Key idea: Delta specs — instead of documenting the whole system, you document only what's being ADDED, MODIFIED, or REMOVED for each change.

Workflow: /opsx:propose → /opsx:apply → /opsx:sync

Best for: Solo developers or small teams iterating fast on existing codebases.

📖 GitHub: Fission-AI/OpenSpec · openspec.dev

🔹 Spec Kit (by GitHub)

Philosophy: Standardized, phase-based. Works across 30+ AI coding assistants. Think of it as "the GitHub Actions of SDD" — opinionated templates, extensible community.

Key idea: The Constitution — immutable project rules that the AI must always obey (architecture patterns, coding standards, security policies).

Workflow: /speckit.constitution → /speckit.specify → /speckit.plan → /speckit.tasks → /speckit.implement

Best for: Teams wanting a standardized, agent-agnostic process with community extensions.

📖 GitHub: github/spec-kit · GitHub Blog

🔹 BMAD (Breakthrough Method for Agile AI-Driven Development)

Philosophy: Multi-agent team simulation. Heavyweight but comprehensive. Simulates an entire cross-functional team: PM, Architect, Developer, QA.

Key idea: Agent Personas — each phase is handled by a specialized AI agent with a distinct role, responsibilities, and handoff criteria.

Workflow: PM drafts PRD → Architect creates spine + ADRs → Developer builds → QA verifies

Best for: Complex greenfield projects, enterprise systems, teams needing formal Agile ceremony.

📖 GitHub: bmad-code-org/BMAD-METHOD · bmad-method.org

Knowledge Check

1. What is the primary artifact in spec-driven development?

  • The AI chat history
  • The pull request description
  • The specification document
  • The test suite output
✅ Correct! The spec is the single source of truth — everything else flows from it.
❌ Not quite. In SDD, the specification document is the primary artifact. Chat histories are ephemeral; specs are persistent.

2. Which methodology introduced the concept of "delta specs"?

  • Spec Kit (GitHub)
  • OpenSpec (Fission AI)
  • BMAD (bmad-code-org)
  • AWS Kiro (Amazon)
✅ Correct! OpenSpec uses delta specs to document only ADDED, MODIFIED, or REMOVED requirements per change.
❌ That's not right. Delta specs are an OpenSpec concept — they let you document changes incrementally instead of rewriting full system specs.

3. Which SDD methodology simulates a cross-functional team with agent personas?

  • BMAD (bmad-code-org)
  • Spec Kit (GitHub)
  • OpenSpec (Fission AI)
  • Tessl (Guy Podjarny)
✅ Correct! BMAD defines specialized personas — PM, Architect, Developer, QA — each with distinct responsibilities.
❌ Not quite. Agent personas are a BMAD concept. BMAD simulates a full engineering team using role-specific AI agents.

4. What problem does a "Constitution" solve in Spec Kit?

  • It generates test cases automatically
  • It creates delta specs for brownfield apps
  • It enforces immutable project rules the AI must follow
  • It assigns work to specialized agent personas
✅ Correct! The Constitution defines non-negotiable rules — architecture patterns, coding standards, security policies — that the AI cannot override.
❌ The Constitution is Spec Kit's mechanism for enforcing immutable project rules — things the AI must always follow regardless of the task.
