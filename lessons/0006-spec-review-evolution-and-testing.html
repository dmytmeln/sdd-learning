Lesson 6 — Spec Evolution, Review Playbook & Spec-to-Test Transformation

How to mutate specs, conduct rigorous human reviews of AI-authored artifacts, audit generated code, and transform BDD specs directly into automated test suites

1. How to Change a Specification (Spec Mutation Lifecycle)

A frequent question in SDD is: "What happens when requirements change?" In OpenSpec, how you change a spec depends entirely on where the change sits in the lifecycle:

Scenario State of the Project Correct Mutation Procedure
A. In-Flight Discovery
(During /opsx:apply)		 Change workspace is active in openspec/changes/<id>/ The "Pause & Amend" Rule:
1. Halt agent code generation.
2. Directly edit specs/<cap>/spec.md (adjust GIVEN/WHEN/THEN) and design.md.
3. Insert new tasks in tasks.md.
4. Re-run openspec validate <id>.
5. Resume /opsx:apply.
B. Post-Archive Evolution
(Feature already deployed)		 Previous change was archived; living spec exists in openspec/specs/ The New Delta Rule:
1. Never edit archived folders in openspec/archive/.
2. Propose a new change: /opsx:propose update-tag-limits.
3. In the new delta spec, write under ## MODIFIED Requirements.
4. When archived, it automatically updates the living spec.
C. Living Spec Refactoring
(Structural cleanup)		 Reorganizing capabilities in openspec/specs/ without behavior changes Directly rename or split files within openspec/specs/ and validate with openspec validate --all.

2. Recommended Human Review Flow (The 4-Stage Gate)

The entire point of Spec-Driven Development is that human review shifts left — from reviewing thousands of lines of raw code diffs to reviewing structured intent. Here is the recommended 4-stage review protocol:

  [Stage 1: Proposal Review] ──► [Stage 2: Design Review] ──► [Stage 3: Delta Spec Review] ──► [Stage 4: Tasks Review]
       Scope & Non-Goals             Architecture & Seams           BDD & Invariants               Phasing & Test Gating

Stage 1: Reviewing proposal.md (Product & Boundaries)

  • Is the Problem Statement clear? Does it solve a real user pain point?
  • Are Non-Goals explicitly stated? Did the AI add speculative features (e.g. nested tags when you only wanted flat tags)? Cut them immediately.
  • Are User Roles & Multi-Tenancy defined? Is it clear whether this is user-private or global?

Stage 2: Reviewing design.md (Architecture & Seams)

  • Package-by-Feature Adherence: Does it match the existing project conventions (e.g. org.example.library.tag.*)?
  • Database Migration Integrity: Are Liquibase/Flyway changesets fully typed, with foreign keys, unique constraints, and indexes?
  • Error Handling: Are HTTP error statuses (400, 404, 409) and error codes (error.tag.already_exists) explicitly cataloged?
  • Security Seam: How does authentication work? Is userId extracted securely from UserPrincipal?

Stage 3: Reviewing specs/<cap>/spec.md (Behavior & Contracts)

  • Deterministic GIVEN / WHEN / THEN: Can an automated test be written directly from every scenario?
  • Edge Cases Covered: What happens on null inputs, boundary values (0 tags, 50 tags, 51 tags), and special characters?
  • Requirement IDs: Does every rule have a unique key (e.g., REQ-TAG-001)?

Stage 4: Reviewing tasks.md (Sequencing & Test Checkpoints)

  • Dependency Order: Does it follow: Database → Entity/Repo → Service/Logic → Controller → Tests?
  • Granularity: Is each task small enough to be verified independently?

3. Code Review Playbook: Auditing AI-Generated Code Against Specs

When the AI completes /opsx:apply, how do you review the code without getting overwhelmed? You perform a Spec-Conformance Code Review:

Review Check What to Look For Red Flags (Reject Code If Found)
1. Spec-to-Code Conformance Compare the modified files directly against tasks.md and design.md. AI created extra helper classes or utility methods not specified in design.md (speculative generality).
2. Constraint Enforcement Seam Verify where business rules (e.g. 50-tag limit) are checked. Rule is checked in the controller instead of the domain service layer, or not checked at all.
3. Database Query Efficiency Examine Spring Data JPA repository methods and generated SQL. N+1 query problems; fetching full entity collections in memory instead of using database counts or projections.
4. Test Assertion Quality Inspect test assertions for each requirement ID. Trivial tests that only assert assertNotNull(response) without verifying the exact GIVEN/WHEN/THEN contract values.

4. Spec-to-Test Transformation (The Testing Pyramid in SDD)

💡 Is it good practice to convert spec.md into tests?

Yes — it is the single most valuable practice in Spec-Driven Development.

When every requirement in spec.md maps directly to an automated test, you achieve 100% Behavioral Traceability. If a future refactor breaks a requirement, the exact requirement ID will fail in CI.

The SDD Test Type Matrix: What Level of Test for What Requirement?

Test Type What it Tests from spec.md Spring Boot Tooling Speed
Unit Test Pure domain logic, input normalization (trim/lowercase), limit checks, custom validators. JUnit Jupiter, Mockito, AssertJ ⚡ < 5 ms
Slice Test (Web) HTTP endpoints, status codes (201, 400, 404), JSON serialization, authentication principal extraction. @WebMvcTest, MockMvc 🚀 ~100 ms
Integration Test Database constraints (unique index, cascading delete), Liquibase schema validity, complex queries. @SpringBootTest, Testcontainers (PostgreSQL) 🐢 ~1-3 s

5. Real-World Example: Converting REQ-TAG-001 into Tests

Let's take a requirement from our delta spec and show its exact transformation into tests across the pyramid:

The Delta Spec Requirement:

### REQ-TAG-001: User Tag Creation
An authenticated user MUST be able to create a custom tag scoped uniquely to their account.
- **GIVEN** an authenticated user with ID 42
- **WHEN** a POST request is sent to `/api/v1/users/me/tags` with payload `{"name": "science-fiction"}`
- **THEN** a new Tag entity is persisted with `user_id = 42` and `name = "science-fiction"`
- **AND** a `201 Created` status is returned with body `TagDto(id=1, name="science-fiction")`

Transformation 1: Web Slice Test (MockMvc)

@WebMvcTest(TagController.class)
class TagControllerTest {

    @Autowired private MockMvc mockMvc;
    @MockBean private TagService tagService;

    @Test
    @DisplayName("REQ-TAG-001: Should create tag and return 201 Created")
    void shouldCreateTag_whenValidPayload() throws Exception {
        // GIVEN
        var request = new CreateTagRequest("science-fiction");
        var expectedDto = new TagDto(1L, "science-fiction");
        when(tagService.createTag(eq(42L), any())).thenReturn(expectedDto);

        // WHEN & THEN
        mockMvc.perform(post("/api/v1/users/me/tags")
                .with(user(new UserPrincipal(42L, "user@example.com", List.of())))
                .contentType(MediaType.APPLICATION_JSON)
                .content("""{"name": "science-fiction"}"""))
                .andExpect(status().isCreated())
                .andExpect(jsonPath("$.id").value(1))
                .andExpect(jsonPath("$.name").value("science-fiction"));
    }
}

Transformation 2: Persistence Integration Test (Testcontainers PostgreSQL)

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class TagRepositoryIT {

    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired private TagRepository tagRepository;
    @Autowired private UserRepository userRepository;

    @Test
    @DisplayName("REQ-TAG-001: Should persist Tag entity with correct user foreign key")
    void shouldPersistTag_withUserRelationship() {
        // GIVEN
        var user = userRepository.save(User.builder().email("test@lib.com").build());
        var tag = Tag.builder().name("science-fiction").user(user).build();

        // WHEN
        var saved = tagRepository.save(tag);

        // THEN
        assertThat(saved.getId()).isNotNull();
        assertThat(saved.getName()).isEqualTo("science-fiction");
        assertThat(saved.getUser().getId()).isEqualTo(user.getId());
    }
}

7. Knowledge Check

1. If you discover an edge case while /opsx:apply is generating code, what is the best practice?

  • Let the AI finish, delete all tests, and push to main
  • Pause code generation, update the spec & design first, then resume apply
  • Directly fix the code in IDE and leave the spec untouched
  • Run openspec archive immediately to bypass validation
✅ Correct! Always pause and update the spec first. The specification must remain the single source of truth at all times.
❌ In SDD, you must pause and amend the specification and design first before modifying code. Otherwise, your specs suffer from immediate drift.

2. Which type of automated test is best suited for verifying database unique constraints and Liquibase schema validity?

  • Pure Unit Test with Mockito
  • Frontend Playwright E2E UI Test
  • Repository Integration Test with Testcontainers (real database)
  • Static SonarQube Lint Check
✅ Correct! Database constraints (unique indexes, FK cascade) must be verified against a real database using Testcontainers.
❌ Database constraints and schema migrations require a real database (e.g. Testcontainers PostgreSQL) to verify that database-level indexes and constraints fire correctly.

3. Why should requirement IDs (e.g. REQ-TAG-001) be referenced in automated test method names or @DisplayName?

  • To achieve 100% bidirectional traceability between specification requirements and test assertions
  • To make Java compile bytecode 50% faster
  • To allow the AI to bypass unit test execution in CI
  • To automatically delete Git branches on PR merge
✅ Correct! Referencing requirement IDs in tests creates full traceability: when a test fails, you immediately know which exact spec clause was violated.
❌ Requirement IDs provide direct traceability between the specification document and the automated test suite.
