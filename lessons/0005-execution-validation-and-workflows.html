Lesson 5 — Execution, Validation & Real-World Workflows

Executing /opsx:apply, validating integrity via CLI, merging deltas into living documentation, and mastering multi-change workflows

1. The Execution Phase: /opsx:apply

Once your change artifacts (proposal.md, design.md, tasks.md, and delta specs) are validated, you trigger execution in your AI chat:

/opsx:apply 20260830-book-tags

How the Agent Operates Under /opsx:apply:

  1. Reads the Contract: The agent loads design.md, the delta spec, and tasks.md into its active context window.
  2. Sequential Task Traversal: It works through tasks one by one, checking off completed items in tasks.md (- [x] 1.1 Create Liquibase migration...).
  3. Test Gating: After completing each phase, it executes the corresponding unit or integration test suite to verify no regressions occurred.
⚠ The Golden Rule: Mid-Flight Spec Amendments

What if during /opsx:apply, you or the agent discover an unforeseen edge case (e.g. tag names need emoji filtering)?

Never edit code to deviate from the spec! Instead:

  1. Pause code generation.
  2. Update the requirement in specs/tag/spec.md and design.md.
  3. Add a new task in tasks.md.
  4. Resume /opsx:apply.
The spec remains the single source of truth at all times.

2. Validation & Integrity: openspec validate

Before and after applying changes, you can verify repository integrity using the CLI in your terminal:

# Validate a specific change workspace
openspec validate 20260830-book-tags

# Validate all active changes and living specs
openspec validate --all

What openspec validate Checks:

  • Schema Completeness: Verifies that proposal.md, design.md, and tasks.md contain all mandatory headers.
  • Requirement Identifiers: Ensures all requirements in delta specs have valid, non-duplicate keys (e.g. REQ-TAG-001).
  • Cross-References: Detects broken markdown links between tasks and spec files.
  • Task Progress: Warns if tasks are unchecked prior to archiving.

3. Living Documentation Sync & Archiving

When all tasks in tasks.md are checked and tests pass, you finalize the change:

/opsx:archive 20260830-book-tags

This command performs two coordinated operations:

Operation A: Spec Reconcilation (Sync)

OpenSpec merges the delta spec into the permanent openspec/specs/ folder:

  • ## ADDED items are appended as permanent capabilities in openspec/specs/tag/spec.md.
  • ## MODIFIED items update the target capability's living specification.
  • ## REMOVED items are removed from the living specification.

Operation B: Historical Archiving

The entire directory openspec/changes/20260830-book-tags/ is moved to openspec/archive/20260830-book-tags/. This preserves a permanent, auditable Git history of the exact proposal, architectural design, and tasks that produced the feature.

4. Real-World Patterns & Best Practices

Pattern 1: Git Feature Branches + OpenSpec

Each Git branch encapsulates its own active change directory:

git checkout -b feature/book-tags
# creates openspec/changes/20260830-book-tags/
# code & spec developed together
git commit -m "feat(tag): implement user book tags according to spec"
# /opsx:archive moves change to archive/
git merge main

Pattern 2: Brownfield Legacy Onboarding

How to introduce OpenSpec to an existing project like Personal-Library without documenting everything upfront:

  1. Day 1: Run openspec init. Leave openspec/specs/ completely empty.
  2. First Feature: Propose a new feature (e.g. 20260830-book-tags) with delta specs.
  3. On Archive: OpenSpec automatically seeds openspec/specs/tag/spec.md as your first living spec!
  4. Over Time: Every new feature or refactor naturally populates your living documentation without any artificial documentation sprints.

7. Knowledge Check

1. What should you do if an unforeseen design flaw is discovered during /opsx:apply?

  • Quietly change the Java code and leave the spec outdated
  • Pause, amend the delta spec and design.md first, then resume apply
  • Delete the entire repository and restart from scratch
  • Ignore the flaw and push to production
✅ Correct! In SDD, you always update the specification first to maintain it as the single source of truth.
❌ Always update the specification and design first before modifying code. This preserves the spec as the single source of truth.

2. How does OpenSpec solve the brownfield documentation problem?

  • It forces developers to document the entire codebase in week 1
  • It uses AI to delete undocumented legacy code automatically
  • It seeds living documentation incrementally as new feature deltas are archived
  • It generates binary files that only compilers can read
✅ Correct! OpenSpec builds living documentation incrementally over time through archived delta specs, avoiding upfront documentation fatigue.
❌ OpenSpec seeds living specs incrementally with every archived change, so you never have to "boil the ocean" on an existing codebase.
