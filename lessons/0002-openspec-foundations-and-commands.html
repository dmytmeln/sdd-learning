Lesson 2 — OpenSpec Foundations, Architecture & Command Suite

A rigorous dive into the mental model, directory architecture, dual-interface mechanics, and token economics of OpenSpec

1. The Fundamental Problem: Context Drift & The "Boil the Ocean" Trap

Before understanding OpenSpec, we must understand the two failure modes that plague software teams using AI coding assistants:

Failure Mode A: Vibe Coding (Zero Specification)

In unstructured chat, the developer prompts iteratively. By step 12, the LLM loses attention on decisions made in step 2. It introduces subtle regressions, ignores earlier constraints, and invents conflicting database schemas because the prompt history exceeds optimal reasoning thresholds.

Failure Mode B: Monolithic Spec-First ("Boil the Ocean")

Traditional upfront specification methodologies demand documenting every existing controller, entity, and edge case before starting work. In a production brownfield app like Personal-Library, writing a 200-page specification upfront is economically impractical and doomed to rot.

OpenSpec’s Solution: The Delta Specification paradigm. You maintain living documentation that grows incrementally. Every change introduces a tiny, isolated "delta" that documents only what is ADDED, MODIFIED, or REMOVED.

2. Directory Anatomy: How OpenSpec Organizes State

OpenSpec stores everything in pure, version-controlled Markdown directly in your repository root:

Personal-Library/
├── openspec/
│   ├── specs/                       ◄── LIVING SPECIFICATIONS (Permanent Source of Truth)
│   │   ├── book-catalog/spec.md     ◄── Describes global books & translations
│   │   ├── collection-tree/spec.md  ◄── Describes 4-level hierarchy rules
│   │   └── reading-progress/spec.md ◄── Describes status transitions & goals
│   │
│   ├── changes/                     ◄── ACTIVE CHANGE WORKSPACES (In-Flight Work)
│   │   └── 20260830-book-tags/      ◄── Scoped directory for a specific feature
│   │       ├── proposal.md          ◄── "Why & What" (Scope, non-goals, user value)
│   │       ├── design.md            ◄── "How" (Architecture, schema, security, seams)
│   │       ├── tasks.md             ◄── Ordered, checkable agent work breakdown
│   │       └── specs/               ◄── Delta Specs for this change
│   │           └── tag/spec.md      ◄── Exact ADDED/MODIFIED/REMOVED requirements
│   │
│   └── archive/                     ◄── AUDIT LOG (Completed & synced changes)
│       └── 20260820-rating-system/  ◄── Preserved historical context of past decisions
└── library-app/                     ◄── Actual Spring Boot source code

3. The Dual Interface: Terminal CLI vs. AI Slash Commands

One of the most frequent beginner mistakes is confusing where commands run. OpenSpec is strictly split across two execution environments:

Environment 1: Terminal Shell (CLI Commands)

Used by you (the developer) in PowerShell/Bash to manage files, inspect repository health, validate schemas, and view dashboards:

CommandWhen to runWhat it does under the hood
openspec init Once per project Creates openspec/ structure and injects slash command configuration for Cursor / Claude / Copilot.
openspec list Daily workflow Scans openspec/changes/ and openspec/specs/, reporting active changes and completion percentages.
openspec show <id> Before applying Outputs status breakdown, completed vs. pending tasks, and spec delta counts for change <id>.
openspec validate <id> During spec review Lints markdown files for required sections, broken markdown links, and requirement identifier integrity.
openspec view Planning / Reviews Launches a lightweight local web UI to browse active changes, dependencies, and living specs graphically.

Environment 2: AI Chat Interface (Slash Commands)

Used inside your AI coding assistant (Antigravity, Cursor, Claude Code, Copilot) to direct reasoning:

CommandPhaseWhat the AI does
/opsx:explore <topic> Discovery Thinking Partner. Probes codebase, searches entities, reveals hidden constraints. Writes zero files.
/opsx:propose <id> Specification Generates the change folder with proposal.md, design.md, tasks.md, and delta specs.
/opsx:apply <id> Implementation Executes tasks.md item by item, adhering strictly to the delta spec constraints.
/opsx:sync <id> Documentation Reconciles delta spec requirements into the main openspec/specs/ living documentation.
/opsx:archive <id> Completion Verifies tasks are done, runs sync, and moves change folder to openspec/archive/.

4. 🎯 Obligatory Hands-On Practice Assignment

🛠️ Assignment 2.1: Bootstrapping OpenSpec on Personal-Library

Goal: Transform D:\Personal-Library into an OpenSpec-governed repository and verify CLI runtime health.

Step 1: Check Runtime Prerequisites

Open PowerShell and verify that Node.js (v20.19.0+) is installed:

node -v
npm -v
Step 2: Install OpenSpec CLI Globally 
npm install -g @fission-ai/openspec@latest

Verify installation: openspec --version

Step 3: Initialize OpenSpec in Personal-Library 
cd D:\Personal-Library
openspec init

Select your primary AI assistant/editor when prompted (e.g. Cursor, Claude Code, Copilot, or Generic).

Step 4: Inspect Generated Scaffolding

Verify that the following directory structure was created:

D:\Personal-Library\openspec\
├── specs/
└── changes/
Step 5: Run Verification Command

Execute the CLI listing command:

openspec list
✅ Verification Criteria & Deliverable:
  • openspec list executes with exit code 0 and reports 0 active changes.
  • The openspec/ directory is tracked in Git status.

5. Token Economics: Why SDD Makes Agents Smarter

Why does an AI generate cleaner Spring Boot code when governed by OpenSpec?

  [ Monolithic Vibe Prompting ]
  Prompt: Entire Codebase + Chat History (120,000 tokens)
  ─────────────────────────────────────────────────────────────
  Attention Decay Curve:
  100% ────┐
   50%     └──────────┐
    0%                └──────────────────────── (High Hallucination Zone)

  [ OpenSpec Bounded Delta Prompting ]
  Prompt: proposal.md + design.md + delta spec.md (12,000 tokens)
  ─────────────────────────────────────────────────────────────
  Attention Retention:
  100% ──────────────────────────────────────── (Peak Reasoning & Determinism)

By bounding the agent's context to a single change delta, we operate in the model's peak reasoning zone. The AI doesn't get confused by unrelated controllers or entities.

6. Knowledge Check

1. Where are living, permanent system specifications stored in OpenSpec?

  • openspec/changes/<id>/
  • openspec/specs/
  • .github/workflows/
  • openspec/archive/
✅ Correct! openspec/specs/ holds the permanent living specifications of the master codebase.
❌ Not quite. openspec/specs/ is the permanent home for living specs. changes/ is only for temporary in-flight workspaces.

2. Which command is strictly a terminal CLI command, NOT an AI slash command?

  • /opsx:explore
  • /opsx:apply
  • openspec validate
  • /opsx:propose
✅ Correct! openspec validate is a terminal CLI command run by the developer to verify markdown schema integrity.
❌ openspec validate is a CLI command run in the terminal. All commands starting with /opsx: are AI slash commands.

3. What is the primary operational rule of the /opsx:explore command?

  • It only probes and analyzes; it creates zero files on disk
  • It immediately generates the Java entity and migration files
  • It merges all delta specs directly into master living specs
  • It deletes previous archived changes to save disk space
✅ Correct! /opsx:explore is purely a thinking partner session for investigation — it writes zero files to disk.
❌ /opsx:explore is strictly an investigation step. It generates no files and writes no code until you transition to /opsx:propose.
