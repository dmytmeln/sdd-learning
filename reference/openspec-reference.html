OpenSpec Reference Manual

Complete Technical Architecture, Command Matrix, Grammar & Operational Patterns

1. Architecture & Mental Model

OpenSpec is a change-centric, repo-native Spec-Driven Development framework. It replaces ephemeral AI chat context with durable, version-controlled Markdown artifacts stored directly inside the target repository.

project-root/
└── openspec/
    ├── specs/                       ← LIVING DOCUMENTATION (System Source of Truth)
    │   ├── catalog/spec.md
    │   ├── collection/spec.md
    │   └── auth/spec.md
    ├── changes/                     ← ACTIVE DELTA WORKSPACES (In-flight changes)
    │   └── 20260830-add-tags/
    │       ├── proposal.md          ← Intent, scope & non-goals (Why & What)
    │       ├── design.md            ← Architecture, schemas, trade-offs (How)
    │       ├── tasks.md             ← Ordered, checkable agent work breakdown
    │       └── specs/               ← Delta Specs (Exact requirement diffs)
    │           └── tag/spec.md      ← ADDED / MODIFIED / REMOVED requirements
    └── archive/                     ← HISTORICAL RECORD (Archived changes after sync)
        └── 20260825-book-ratings/
            ├── proposal.md
            └── ...
💡 The Living Spec vs. Delta Split
  • Living Specs (openspec/specs/): Describe the current capabilities of the master codebase. They are permanent, modular, and capability-focused.
  • Delta Specs (openspec/changes/<id>/specs/): Describe only the net changes (ADDED, MODIFIED, REMOVED) for a specific work item. Once implemented, these deltas are folded into the living specs.

2. The Unified Command Matrix

OpenSpec distinguishes strictly between CLI Commands (run in your shell for repository orchestration) and AI Slash Commands (typed into the AI agent's chat window for cognitive collaboration).

Command Context Type Primary Purpose & Behavior
openspec init Terminal CLI Bootstraps the openspec/ folder structure and configures slash prompts for chosen IDE/Agent.
openspec list Terminal CLI Enumerates active change proposals, their status, and existing living specifications.
openspec show <id> Terminal CLI Displays formatted status, task completion count, and artifact summary for change <id>.
openspec validate <id> Terminal CLI Validates markdown schema compliance, missing requirement keys, and broken links across change artifacts.
openspec view Terminal CLI Launches a local interactive web dashboard visualizing changes, living specs, and progress.
openspec archive <id> Terminal CLI Directly moves an active change to archive/ and triggers sync into openspec/specs/.
/opsx:explore AI Chat Slash Thinking-Partner Mode: Deeply investigates existing code, discovers edge cases, and weighs trade-offs. Produces no disk files.
/opsx:propose <id> AI Chat Slash Generates the complete change workspace: proposal.md, design.md, tasks.md, and initial delta specs.
/opsx:apply <id> AI Chat Slash Instructs the AI agent to execute tasks sequentially against the delta spec, running tests after each task.
/opsx:sync <id> AI Chat Slash Reconciles delta specs into the global openspec/specs/ living documentation tree.
/opsx:archive <id> AI Chat Slash Verifies tasks are 100% complete, executes spec sync, and files the change folder into archive/.

4. Delta Specification Grammar

Every delta spec under openspec/changes/<id>/specs/<capability>/spec.md strictly categorizes behavioral changes using three primary top-level headers:

# Capability: Tag Management

## ADDED Requirements

### REQ-TAG-001: User Tag Creation
A user MUST be able to create a custom tag scoped uniquely to their account.
- **GIVEN** an authenticated user with ID 42
- **WHEN** a POST request is sent to `/api/v1/users/me/tags` with name `"sci-fi"`
- **THEN** a new Tag entity is created with ID and name trimmed to lowercase
- **AND** a 201 Created response is returned with the created `TagDto`

### REQ-TAG-002: Tag Name Uniqueness
Tag names MUST be unique per user (case-insensitive).
- **GIVEN** user 42 already owns a tag named `"history"`
- **WHEN** user 42 attempts to create a tag named `"HISTORY"` or `" history "`
- **THEN** the operation MUST fail with 400 Bad Request (`error.tag.already_exists`)

## MODIFIED Requirements

### REQ-LB-004: LibraryBook Response Payload
- **WAS**: Returned `LibraryBookDto` containing ID, status, rating, and location.
- **NOW**: MUST include an additional field `tags: List<TagDto>` populated with all tags associated with the library book.

## REMOVED Requirements

### REQ-LEGACY-009: Deprecated Freeform Book Memo
- **REASON**: Superseded by structured Notes and Tags system.
- **ACTION**: Remove `memo` column from `library_books` table.

• Data Model & Database Migrations

• Error Handling & Security Policy
• Trade-off Evaluation & Alternatives 		Explicitly addresses edge cases, database constraints (unique indexes, FK cascading), and architectural rules.
tasks.md • Phase 1: Persistence & Domain Model
• Phase 2: Service Layer & Business Rules
• Phase 3: Web Controller & DTO Mapping
• Phase 4: Integration & Unit Tests
• Phase 5: Verification & Cleanup 		Strictly ordered checkbox checklist (`- [ ]`). Each item must be verifiable with an automated test or assertion.

6. Context Window Economics

Why OpenSpec avoids dumping entire codebases into prompts:

Approach Token Footprint Reasoning Quality Risk Profile
Monolithic Prompting 100k – 200k tokens Degrades rapidly; high attention decay High context hallucination, silent overwrites
OpenSpec Delta Scoping 10k – 30k tokens Peak reasoning retention Deterministic, test-gated execution

7. Trade-offs: Pros vs. Cons

Advantages (Pros) Trade-offs & Overhead (Cons)
Zero Greenfield Monopoly: Designed natively for brownfield codebases via delta specifications. Upfront Ceremony: Requires 5–10 minutes of spec review before code generation begins.
Bounded Agent Context: Keeps AI strictly within the declared capability boundary. Discipline Overhead: If a human modifies code out-of-band without updating specs, drift can occur.
Living Documentation: Specs automatically stay fresh via /opsx:archive syncing. Tool Dependency: Requires Node.js runtime and slash command setup in developer environment.
Deterministic Auditability: Git commits directly reference specific proposal IDs and tasks. Overkill for Trivial Fixes: Single-line typo or CSS fixes don't warrant a full proposal cycle.

8. Spec Mutation & Evolution Lifecycle

Lifecycle Phase Trigger Condition Mandatory Procedure
In-Flight Discovery
(During /opsx:apply)		 Unforeseen edge case, missing field, or broken assumption found while generating code. Pause & Amend Rule:
1. Halt code generation.
2. Amend specs/<cap>/spec.md and design.md directly.
3. Insert new tasks into tasks.md.
4. Run openspec validate <id>.
5. Resume /opsx:apply.
Post-Archive Evolution
(Next release/feature)		 Business requirements evolve after previous change was completed and archived. New Delta Rule:
1. Run /opsx:propose <new-change-id>.
2. Author requirements under ## MODIFIED Requirements.
3. Archiving folds changes into the master openspec/specs/ living docs.
Living Spec Refactor
(Structural cleanup)		 Splitting or merging capability files in openspec/specs/ without altering behavior. Reorganize files in openspec/specs/ and verify integrity via openspec validate --all.

9. The Human Review & Code Review Playbook

4-Stage Spec Review Checklist

  • 1. Proposal Check: Scope is tight, user roles defined, non-goals explicitly state what will NOT be built.
  • 2. Design Check: Package-by-feature conventions respected, Liquibase changesets complete, error catalog enumerated.
  • 3. Delta Spec Check: Every rule is in BDD GIVEN / WHEN / THEN format with a unique ID (e.g. REQ-TAG-001).
  • 4. Tasks Check: Sequenced in strict dependency order (Persistence → Service → Controller → Tests).

AI-Generated Code Review Playbook

  • Conformance Audit: Check git diff against tasks.md. Reject any unapproved classes or speculative utilities.
  • Seam Verification: Ensure business constraints are enforced in domain services, not leaky controllers.
  • Query Performance: Verify JPA repository queries avoid N+1 fetches and use projections/counts where appropriate.
  • Test Traceability: Verify every requirement ID has a matching automated test method.
