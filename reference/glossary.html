SDD Glossary

Spec-Driven Development — Key Terms & Definitions

TermDefinition
Spec-Driven Development (SDD) An engineering methodology where a written specification — not ad-hoc prompts — serves as the primary contract and single source of truth that governs AI code generation.
Vibe Coding Unstructured, conversational prompting of an AI coding assistant with no formal spec. Fast to start, but suffers from context drift, hallucination, and architectural debt.
Specification (Spec) A structured document (usually Markdown) that captures requirements, architecture, constraints, and acceptance criteria for a piece of work. The primary artifact in SDD.
Living Spec / Living Documentation A specification that evolves alongside the codebase. Changes to code require corresponding updates to the spec, keeping them in sync.
Delta Spec An OpenSpec concept: instead of rewriting the full system spec, you describe only what was ADDED, MODIFIED, or REMOVED for a given change.
Constitution A Spec Kit concept: a set of immutable project rules (architecture patterns, coding standards, security policies) that the AI must always follow.
Agent Persona A BMAD concept: a role-specific AI agent (Product Manager, Architect, Developer, QA) defined via YAML/Markdown, each with distinct responsibilities and handoff criteria.
Context Drift When an AI agent loses track of earlier decisions during a long session, producing code that contradicts its own prior output.
Context Engineering The discipline of curating what information an AI agent sees — controlling its context window to maximize reasoning quality and minimize hallucination.
Spec-First A taxonomy level where specs are written upfront to guide a task, but may not be maintained after implementation. The lightest SDD approach.
Spec-Anchored A taxonomy level where living specs are maintained throughout the feature lifecycle. Code changes require spec updates. Used by OpenSpec, Spec Kit, and Kiro.
Spec-as-Source The most radical SDD paradigm: humans edit only specs; source code is 100% generated and treated as a disposable build artifact. Pioneered by Tessl.
PRD (Product Requirements Document) A formal document defining what to build and why. In BMAD, generated by the Product Manager persona.
ADR (Architecture Decision Record) A short document capturing a significant architecture decision, its context, and consequences. Used in BMAD to create durable context.
Human-in-the-Loop A workflow design where a human reviews and approves AI-generated artifacts at defined checkpoints before execution proceeds.
